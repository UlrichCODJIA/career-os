# Server-side soak monitoring (staged)

The scan worker runs independently in Docker. The monitoring job must also live on the VM if the laptop can be off. This runbook is staged, not installed: verify the VM's actual deployment path, image, Compose project, evidence volume, and access controls before enabling a timer. Leave the current laptop check enabled until two VM executions are observed and their results reconciled.

`bun run release:inspect-soak` is a read-only aggregate preflight. It reports counts and `preflightCountsReady`, but **does not** verify the release commit, registry digest, or human decisions, and does not start the soak. A zero exit status means the query succeeded, not that release is ready. `scripts/run-soak-monitor.sh` runs this command in a one-off worker container while `SOAK_STARTED_AT` is unset. Once the full commit-bound `release:check-soak-start` gate reports `ready: true` and an operator sets a fresh start timestamp, the same wrapper instead captures one immutable snapshot in the existing release-evidence volume. It never sets the timestamp itself.

## Server install after private SSH is verified

1. Verify the checked-out or extracted release, release commit, approved registry digest, running Compose project, database health, and existing evidence volume. Do not point monitoring at a source checkout that differs from the deployed image. Preserve the old snapshots as-is. Build with `CAREER_OS_RELEASE_COMMIT` set to the exact verified archive commit so the image contains a valid `/app/.release-commit`; the full start gate must match this marker to `RELEASE_COMMIT`.
2. Deploy this code only through the release procedure, including a fresh verified backup before changing the VM. Keep the soak timer disabled. The wrapper uses both `compose.yaml` and the private `compose.soak.yaml` override with the verified project directory; running only the public base file would use the wrong VM configuration. Run `CAREER_OS_DEPLOY_DIR=/opt/career-os bash /opt/career-os/scripts/run-soak-monitor.sh` manually and confirm it reports aggregate counts without credentials or source identifiers.
3. Use the reviewed templates in `ops/systemd/career-os-soak-monitor.service` and `.timer`, installed under `/etc/systemd/system` only after confirming `/opt/career-os` is the deployed release. The service runs as `azureuser` and uses its existing passwordless sudo for Docker Compose; it does not add the account to the Docker group. It sets `CAREER_OS_DEPLOY_DIR=/opt/career-os` and reads optional `/etc/career-os/soak-monitor.env`. Before the soak starts, that file must not contain `SOAK_STARTED_AT`. After the full gate passes, record the exact `SOAK_STARTED_AT`, `RELEASE_COMMIT`, and `REGISTRY_DIGEST`; do not set an earlier or fabricated start time. Keep the file root-owned with mode 0600; systemd reads it before switching to the service user.
4. Enable the timer at 06:00 and 18:00 UTC (08:00 and 20:00 Africa/Kigali), with `Persistent=true`. Review the first two manual/timed runs, `systemctl status career-os-soak-monitor.timer`, `journalctl -u career-os-soak-monitor.service`, and private evidence files before retiring the laptop check. Duplicate snapshot attempts are safe because the capture uses exclusive file creation, but do not run two schedulers indefinitely.
5. Alert on command failure, missing executions, and snapshot gaps. A timer alone does not satisfy the release evaluator: the seven-day window still needs at least 14 snapshots, 168 hours of coverage, no gap over 14 hours, and all other release gates. Do not mark a held listing closed or approve an employer-to-board link from this monitor.

An SSH chat handoff is separate from this server timer. It moves the chat and Git state to a matching saved project on a reachable host, but the desktop app's own scheduling should not be assumed to transfer or to run while the laptop is off. Do not expose SSH, the app server, the API, or PostgreSQL publicly merely to support handoff.
